Choosing a setup is linked from start here and the infrastructure guide.
Credentials and access is a shared reference linked where the reader connects
an app or schedules work. History and method remain supporting reading.

Shared pages explain principles with a complete everyday example. Product
chapters explain the relevant controls and differences. There is no requirement
for each product to have the same seven chapters.

Building begins with two reader paths. **Building for fun** covers experiments,
learning, and personal projects with disposable sample data. **Building
seriously** covers business, income, startups, consequential users, and other
people depending on the result. These are about consequences, not project size
or a claim that commercial work requires a different personality or model.
Both paths need review and a way back. The serious path adds appropriate
access boundaries, release review, tests of important behavior, and recovery
before real people or money depend on the work. A small project can cross that
boundary; a large harmless experiment can remain on the curiosity path.

## personal infrastructure starter specification

Use a hypothetical weekly project review throughout. Start with a folder or
document collection the reader already understands. Provide sample notes so
the first exercise needs no private account or paid service.

| section | concrete result the reader should get |
| --- | --- |
| start with one recurring job | a written description of the weekly review, its inputs, and a useful output |
| give your work a home | a small layout for current projects, reference material, and completed work, with one readable entry document |
| separate context, instructions, and task state | an example of a stable preference, a procedure, and a current next action, each stored where it can be corrected |
| connect apps | identify the account and intended operation; begin with a read; understand separate service permissions and action decisions |
| make recurring work observable | manually run the review, check its output, then specify a schedule, destination, and visible failure behavior; distinguish a saved schedule from a successful run |
| recover and change tools | restore a disposable sample file from a backup, export a continuation note, and verify another chat can locate the same current work |

Keep machine/service deployment, remote networking, credential brokers, and
multi-agent infrastructure as optional later material. No claims about Ani's
private setup or actual recovery success are needed for this starter guide.

Everyday work uses similarly bounded hypothetical tasks. A source-linked
research table, a document edit, and a plan prepared from supplied notes each
need a visible result and missing-information handling. Administrative examples
prepare work for review; they do not silently send messages, transact, or change
accounts. Avoid suggesting a recurring process keeps running simply because
its chat exists.

turn these notes into a short plan for this week. keep the decisions i’ve already made, flag questions that need my answer, and reply with a draft i can review.

### planning and acting candidate

Ani requested emphasis on the tradeoff curve between implementing immediately
and planning before acting on October 12. The following is candidate analysis,
with no claimed personal experience or measured optimum. It belongs beside the
first task example, before the deeper coding example, after wording review.

> there’s a tradeoff between planning and finding out by trying. when the task
> is small and easy to undo, a quick first attempt gives you something concrete
> to react to. planning helps more when a decision affects other work or a wrong
> assumption would be expensive to fix.
>
> spend enough time planning to choose a useful next step, then check what
> happens. if you’re wondering whether an idea feels useful, a small prototype
> can answer that. for the notes example, a draft is cheap to change. before building
> something customers will depend on, work through the important decisions and
> failure cases first. more planning has diminishing returns: eventually the
> next useful thing to learn comes from trying a small part of the work.

The accepted everyday task above is now implemented before the coding example.
Its exact accepted span is preserved in the ledger. This planning explanation
remains a separate candidate; approval of the task does not accept it.
